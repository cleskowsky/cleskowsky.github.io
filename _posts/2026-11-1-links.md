## [Cloudflare rate limiting rules](https://developers.cloudflare.com/waf/rate-limiting-rules/)

We use cloudflare waf at work and it's great. Sadly we're having to become more
and more familiar with setting rate limits as awareness of what people are doing
to our poor little web application that lives on the internet improves.

We happen to subscribe to advanced rate limiting and the options for identifying
an individual user and associated rate limit are neat. IP, path, request query
parameter, request body parameter, header value, cookie value, ja4 fingerprint,
and a bunch more.

The capabilities in the free plan are more limited but still quite the nice
tool.

## [What Is Argo CD?](https://argo-cd.readthedocs.io/en/stable/)

Bit of reading of how argocd works this morning. Pretty cool stuff. It looks at
a bunch of application repositories and creates them as running things in k8s.
(services, pods, ingress controller config, etc) Git is the source of truth for
the version of an app that should be running (when git changes, an app is marked
"out of sync") and there's a manual or automatic way to bring the app / running
representation back into alignment.

A single instance of argocd can run inside a cluster or it looks like it can
manage application lists across multiple clusters.

I like this model for application deployment. I wonder if we can get something
like this for ecs ...

## [Your Fargate Autoscaler Doesn't Understand Your JVM (by Default)](https://builder.aws.com/content/3KSu7HdOFfv7hWgVE2P4MDmLuAE/your-fargate-autoscaler-doesnt-understand-your-jvm-by-default-lessons-learned-the-hard-way)

This was great and exactly what we need as we move towards autoscaling in cc and
ocean.

- Ram: scale out not in (maybe?), and make sure the jvm memory max heap size is
  set properly for the size of our container (how big should we make our
  containers?)
- Cpu: Scale out and in for workloads that are cpu bounded
- Busy threads: This is the best metric when all other parameters are well sized
- Disk: Never scale on this (page an operator when disk is low as it's always
  going to be some sort of config related issue or an application that's using
  disk in a weird way - logs or temporary scratch space)

## [Docker Building best practices](https://docs.docker.com/build/building/best-practices/#rebuild-your-images-often)

This was a miss for us. We pinned our base images to shas and proceeded to only
update them when they changed for config reasons our our application changed in
some way. Picking up updates in the lower layers of our image was adhoc and
spotty at best. We're moving to regular builds with a period of soak time with
vulnerability scanning to learn about security bugs.

## [Using LLMs at Oxide](https://rfd.shared.oxide.computer/rfd/0576)

This list of responsible use guidelines for llms at oxide is thoughtful.

I like the breakdown of roles an llm can play within the product creation
process:

- as reader
- writer (distinguish between internal, external, and technical)
- researcher
- debugging
- writing code

Underlying all of it is the idea that humans are still responsible for their
work product and that we can use but must verify always our output.
